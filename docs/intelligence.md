# Code intelligence, context, differential verification, and caches

The controller keeps derived intelligence project-separated and binds every index run to the registered repository, exact revision, parser identity, and content SHA-256. The browser and CLI can request refresh, but cannot upload source, choose a host path, or select an executable. Refresh first synchronizes the registered default branch through the credential-isolated Git bridge and requests a bounded snapshot of ordinary blobs at that exact commit. The bridge excludes oversized or unsupported objects and returns the excluded count.

The current controller parser uses the Go standard-library syntax parser for exact Go declarations/imports and a bounded non-executing lexical adapter for the other supported source extensions. Generated, vendor, and binary inputs are classified without parsing. The analyzer interface is replaceable; Tree-sitter, SCIP, and read-only LSP enrichment remain additive adapters and may not execute workspace commands. Syntax failures are stored as partial evidence, and a later run reuses a blob analysis only inside the same project, repository, blob hash, and parser identity.

Open **Code intelligence** to inspect freshness, language coverage, partial failures, storage, graph queries, deterministic context manifests, baselines/differentials, test-impact records, and cache provenance. `maintainctl intelligence` exposes the matching status, query, refresh, rebuild, context, baseline, differential, impact, cache-list, and cache-purge API operations.

Context compilation orders candidates deterministically, deduplicates identical bytes, reserves the configured output budget first, and records source, version, selection reason, trust, SHA-256, byte/token cost, staleness, inclusion, and exclusion. Only that redacted manifest is durable; packet content and hidden reasoning are not stored.

Verification baselines require an explicit actor, reason, configuration hash, toolchain identity, pack-set hash, exact revision, and bounded observations. Candidate evidence is classified as `pre_existing`, `resolved`, `newly_introduced`, `changed`, or `indeterminate`. A new failure is never converted into baseline acceptance. Test-impact records explain every selected or omitted test and retain the rule that targeted inner-loop tests do not replace a fresh policy-required full final suite.

Cache keys include project, trust domain, kind, and all caller-supplied deterministic input identities. Metadata records both input and object hashes, verified state, size, hit time, and expiry. Key reuse with different input/object hashes conflicts. Rebuild and purge affect derived data only, require administration plus recent reauthentication when authentication is enabled, and append audit events. Cache objects remain in the existing content-addressed artifact boundary; this registry never accepts credentials or browser-provided host paths.
