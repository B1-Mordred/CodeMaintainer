# Code intelligence, context, differential verification, and caches

The checked DOD-11 evidence matrix lives in `config/intelligence-coverage.json`; it ties the implementation, regression tests, browser/CLI/API surfaces, and operator documentation below to machine-verified proof snippets.

The controller keeps derived intelligence project-separated and binds every index run to the registered repository, exact revision, parser identity, and content SHA-256. The browser and CLI can request refresh, but cannot upload source, choose a host path, or select an executable. Refresh first synchronizes the registered default branch through the credential-isolated Git bridge and requests a bounded snapshot of ordinary blobs at that exact commit. The bridge excludes oversized or unsupported objects and returns the excluded count.

The controller remains a static non-CGO binary. It sends one bounded, hash-bound source blob at a time to the internal `code-intelligence` service, which runs non-root with a read-only root, no published port, no mounts, dropped capabilities, and only the internal control network. That service uses the Go standard-library AST for Go and pinned Tree-sitter grammars for Python, JavaScript/TypeScript/TSX, PHP, Rust, C/C++, C#, and R. Grammar identities and versions appear as tool provenance. Generated, vendor, and binary inputs are classified without parsing; syntax errors remain explicit partial evidence.

SCIP and read-only LSP enrichment use a narrow file-evidence interface: an adapter receives bounded bytes and identifiers, never a worktree, command, mount, credential, or workspace-configuration channel. The controller validates every returned path/range/count/confidence before persistence and records rejected providers without leaking their raw error. A later run reuses analysis only inside the same project, repository, blob hash, parser identity, and serialized object identity.

Open **Code intelligence** to inspect freshness, pause state, retention, language coverage, partial failures, storage, graph queries, deterministic context manifests, baselines/differentials, test-impact records, and cache provenance. Operators can compare the newest context manifests, recompute parsed-object integrity, simulate an estimated object against the effective project quota, and warm parsed-source objects only from the registered repository's exact trusted Git snapshot. None of these actions accepts source bytes, a parser command, or a host path.

`maintainctl intelligence` exposes matching operations. In addition to status/query/refresh/rebuild and evidence-list commands, use `compare-contexts <project> <left> <right>`, `verify-cache <project> [--kind source-parse]`, `simulate-cache <project> --kind source-parse --trust-domain trusted --estimated-bytes <bytes>`, and `warm-cache <project>`. Cache verification is read-only: supported object kinds are reserialized and rehashed, while unsupported kinds report `unavailable` instead of a false pass. Simulation does not reserve capacity or evict data.

Context compilation orders candidates deterministically, deduplicates identical bytes, reserves the configured output budget first, and records source, version, selection reason, trust, SHA-256, byte/token cost, staleness, inclusion, and exclusion. Production candidates include the locked task/criteria, immutable effective configuration, verifier policy, repository instructions and authoritative documentation, exact indexed symbol ranges with whole-file fallback, verified canonical project memory, unresolved findings, and recent baseline/differential/test-impact evidence. Only the redacted manifest is durable; packet content and hidden reasoning are not stored.

The workflow indexes the exact synchronized base revision before creating a worktree, captures a policy-defined pre-modification baseline in a fresh verification worker, and creates purpose-bound candidate differentials for targeted, full, and final checks. Baselines require an explicit actor, reason, configuration hash, toolchain identity, pack-set hash, exact revision, and bounded observations. Candidate evidence is classified as `pre_existing`, `resolved`, `newly_introduced`, `changed`, or `indeterminate`. A new failure is never converted into baseline acceptance. Changed paths and indexed symbols produce an immutable test-impact record for every candidate revision; the final gate refuses to advance without its mandatory fresh full-suite policy evidence.

Original baseline, differential, and impact records are immutable. An administrator may explicitly approve a candidate differential as a replacement baseline, append a classification correction, or append a targeted-test override after recent reauthentication and with an audited reason. Replacement baselines are derived only from the candidate observations already stored in that differential. A `newly_introduced` finding cannot be corrected to `pre_existing` or `resolved`; `indeterminate` remains available when evidence is genuinely incomplete. Targeted-test overrides may include or omit an inner-loop test and may expire, but they cannot alter the immutable fresh full-suite requirement.

The Code intelligence page shows these histories beside the original evidence. CLI equivalents are `baseline-updates`, `supersede-baseline`, `corrections`, `correct-differential`, `impact-overrides`, and `override-impact`; run `maintainctl help` for their bounded arguments.

Cache keys include project, trust domain, kind, repository, blob, parser, and schema identities. The actual parsed-blob object is retained in the project-separated SQLite index; cache metadata independently records its complete input hash, serialized object hash, verified state, size, hit time, and expiry. Key reuse with different input/object hashes conflicts. Verification recomputes the same key, input hash, and serialized-object hash from the retained parsed blob. Rebuild removes the derived index and its parsed-blob cache registrations. Rebuild and purge require administration plus recent reauthentication when authentication is enabled, an exact bounded reason, and append audit events. No cache path accepts credentials or browser-provided host paths.

## Configuration

The shared typed Configuration workbench, REST contract, and `maintainctl config` lifecycle expose the same registered controls:

- `intelligence.indexing_enabled` pauses or resumes trusted refresh at system or project scope. A running job uses its immutable acceptance-time snapshot.
- `intelligence.index_retention_days` sets parsed-blob cache expiry from 1 to 3650 days; refresh prunes expired cache registrations, old runs, and unreferenced parsed blobs while retaining the newest run.
- `intelligence.cache_quota_bytes` bounds aggregate registered cache bytes per project. Registration fails transactionally rather than evicting unrelated evidence when the quota is exhausted.
- `intelligence.context_input_tokens` and `intelligence.context_output_reserve_tokens` set per-stage deterministic budgets. Draft validation rejects a reserve that is not below the input budget.
- `verification.clean_final_cache_required` records and enforces the fresh-worker final-gate requirement for publishable candidates.

Changes use the normal draft, validate, dry-run, review, apply, history, rollback, import, and export flow; their scope provenance remains visible in both the Configuration and Code intelligence pages.
